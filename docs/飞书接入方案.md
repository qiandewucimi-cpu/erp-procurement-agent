# 飞书接入方案：外贸 ERP 安全操作 Agent

> 目标：在飞书对话里直接使用现有 Agent，不必每次打开网页。
> 结论：**可行，且改动小**。项目已经是「HTTP API + 干净会话接口 + 独立服务层」的结构，接飞书只需新增一个薄适配层，核心代码零改动。

---

## 0. 一句话结论

推荐 **「飞书自建应用 + 长连接（WebSocket）」**：

- 能双向对话（收消息 + 回消息），不只是单向推送；
- **不需要公网 IP、域名或内网穿透**（长连接是机器人主动连飞书）；
- 复用现有 `POST /agent/chat`（或直接调 `PurchasePOAgent.chat()`），`api.py` / `ui.py` / `erp_agent` 核心**全部不用改**；
- 新增代码约 200~300 行 + 1 个依赖（`lark-oapi`）。

## 1. 现状盘点

### 1.1 运行方式（3 种）

| 方式 | 命令 | 说明 |
|---|---|---|
| Windows 一键启动 | `start_demo.cmd` | 同时拉起 API(8000) + UI(8501)，退出时一并停掉 |
| 分终端启动 | `uvicorn api:app --port 8000` + `streamlit run ui.py` | 手动两个进程 |
| Docker Compose | `docker compose up --build` | api + ui 两个容器，`uploads/` 与数据卷共享 |

### 1.2 对外暴露的接口（关键）

| 层 | 位置 | 形态 | 能否被飞书复用 |
|---|---|---|---|
| Streamlit 聊天页 | `ui.py` :8501 | Web UI | ❌ 面向人，不适合机器人 |
| **FastAPI** | `api.py` :8000 | **标准 HTTP/JSON，12 个端点** | ✅ **接飞书的最佳落点** |
| MCP Server | `mcp_server.py` stdio | 7 个标准 MCP 工具 | ✅ 可接 MCP 客户端（非飞书） |
| 服务层 | `erp_agent/*.py` | 纯 Python（无框架绑定） | ✅ 任意入口可复用 |
| CLI 入口 | 无 | — | ❌ 不存在（`launch_demo.py` 只是启动器） |

**注意：项目早就不是"只有 Web 界面"**，它已经有一套完整 HTTP API：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/health` | 健康检查 + `llm_enabled` / `llm_model` |
| POST | `/agent/chat` | **多轮对话（模型自主编排工具）** ← 接飞书主要就靠它 |
| POST | `/agent/prepare` | 确定性六步流水线（离线可用） |
| POST | `/agent/confirm` | 用「确认提交」口令写入 |
| POST | `/agent/rollback` | 回滚已写入 PO |
| POST | `/agent/detect` | 物料错误检测（可 push 到推送队列） |
| GET | `/orders` `/audit` `/error_reports` | 单据 / 审计 / 错误报告 |
| GET | `/samples` `/materials`，POST `/materials/import` | 示例文件 / 物料档案 |

### 1.3 请求 / 响应格式（决定了适配层怎么写）

**请求**（`ChatRequest`）：
```json
{ "session_id": "abc12345", "messages": [{ "role": "user", "content": "查一下 MAT-FAB-001 的价格" }] }
```

**响应**：
```json
{ "reply": "…回复文本…", "tool_trace": [ … ], "model": "glm-4-flash", "llm_enabled": true }
```

→ 几乎是「为接聊天机器人而生」：**会话 ID + OpenAI 格式 messages + 纯文本回复**，与飞书事件天然可映射。

### 1.4 依赖的外部服务与配置

| 配置项 | 作用 | 默认 |
|---|---|---|
| `LLM_BASE_URL` | 云端(智谱)/本地(Ollama) 的 OpenAI 兼容地址 | 空 → chat 不可用 |
| `LLM_MODEL` | 模型名 | `glm-4-flash` |
| `LLM_API_KEY` | 云端密钥 | 空 |
| `ERP_AGENT_API` | UI 调 API 的地址 | `http://127.0.0.1:8000` |
| `ERP_AGENT_UPLOADS` | 上传目录 | `uploads` |

加载方式：`erp_agent/llm.py` 里 `_load_dotenv()` 自读项目根 `.env`，不覆盖已有环境变量；`.env` 已被 `.gitignore` + `.dockerignore` 双重排除。

### 1.5 完整交互路径（当前）

```
用户 → Streamlit 页 → POST /agent/chat
     → PurchasePOAgent.chat(messages, session_id)
     → 拼接该 session 的历史 → AgentLoop.run()
     → 模型返回 tool_calls → ToolRegistry.call()（7 个工具，确定性实现）
     → SQLite（模拟 ERP）
     → 返回 {reply, tool_trace}
确认写入：用户在对话框输入「确认提交」→ 模型调 confirm_commit → 口令校验 + 幂等 + 审计
```

文件类操作（BOM / 物料档案）走 `resolve_bom_file()`：**只允许 `samples/` 与 `uploads/` 两个白名单目录**，`Path(filename).name` 剥离路径防穿越。

### 1.6 对"接飞书"有利 / 有阻碍的点（诚实盘点）

| 项 | 判断 | 影响 |
|---|---|---|
| 已有标准 HTTP API + 会话 ID | ✅ 有利 | 适配层极薄 |
| 服务层与入口解耦 | ✅ 有利 | 可绕开 HTTP 直接调 `agent.chat()` |
| messages 是 OpenAI 格式 | ✅ 有利 | 飞书文本直接塞进去 |
| `sessions` 是内存字典 `dict[str, list]` | ⚠️ 阻碍 | 单进程有效；多 worker / 重启会丢上下文 |
| BOM 必须是本地白名单文件 | ⚠️ 阻碍 | 飞书上传的文件需先落地到 `uploads/` |
| API 无任何鉴权 | ⚠️ 阻碍 | 本地/内网可接受，公网暴露则不行 |
| 回复是 Markdown | ⚠️ 小阻碍 | 飞书消息需转文本 / `lark_md` |
| 无飞书相关代码 | ℹ️ 事实 | 需要从零写适配层（约 200~300 行） |

## 2. 可行性结论

**完全可行，属于"薄适配"级别的改造。**

原因：机器人本质就是「接收消息 → 调一个会回话的服务 → 把回复发回去」。本项目第二、三步已经现成（`/agent/chat`），只缺第一步和半步回复格式化。安全边界（金额/校验/写入口令）都在工具层内部，接飞书不会触碰它，风险可控。

## 3. 接入方案对比

| 方案 | 能双向对话 | 需公网 | 新增工作量 | 使用体验 | 结论 |
|---|---|---|---|---|---|
| **A. 自定义群机器人（Webhook，仅出站）** | ❌ 只能推送 | 否 | 极低（<30 行） | 单向，只能收通知，不能提问 | 仅能做「物料错误报告自动推送」，替代不了网页 |
| **B. 自建应用 + 事件订阅（Webhook 回调）** | ✅ | **是**（HTTPS 回调地址） | 中 | 好 | 需公网/内网穿透，个人环境麻烦 |
| **C. 自建应用 + 长连接（WebSocket）** | ✅ | **否** | 中 | 好 | ✅ **推荐** |
| D. 改用飞书内置知识问答 / Aily | ✅ 但能力不同 | 否 | 零代码 | 中 | 跑不了本项目的 BOM 工具链，不是同一件事 |

> 说明：方案 D 不是"接入本项目"，而是换一套飞书自带的问答能力（详见 `提出企业ai化建议/飞书AI知识库方案.md`）。它解决的是"查资料"，解决不了"跑 BOM→采购 PO 工具链"，二者互补而非替代。

## 4. 推荐方案：自建应用 + 长连接

```
飞书客户端（单聊 / 群内 @）
        │  ① 长连接 WebSocket（机器人主动连飞书，无需公网）
        ▼
feishu_bot.py（新增适配层）
   ├─ 事件入口：im.message.receive_v1
   ├─ 幂等去重：message_id
   ├─ 会话映射：open_id → session_id
   ├─ 文件落地：下载 file_key → uploads/
   └─ 回复转换：Markdown → 飞书消息
        │  ② 复用 POST /agent/chat（或直接调 agent.chat()）
        ▼
现有 Agent（零改动）：PurchasePOAgent + 7 工具 + SQLite
```

为什么是长连接：飞书开放平台的 Python SDK `lark-oapi` 支持 `ws.Client` 长连接模式，**机器人主动连飞书**，因此不需要公网 IP、域名、备案或 frp/ngrok，本机跑着就能用——这对个人 demo 是决定性优势。

## 6. 实施步骤

1. **建应用**：飞书开放平台 → 开发者后台 → 创建「企业自建应用」，记录 `App ID` / `App Secret`。
2. **开权限**：`im:message`（接收消息）、`im:message:send_as_bot`（以机器人身份发消息）、`im:resource`（下载消息里的文件）。
3. **配事件**：事件订阅方式选 **「使用长连接接收事件」**，订阅 `im.message.receive_v1`。
4. **发布**：创建版本并发布，等管理员审核通过（测试企业/个人可先自测）。
5. **装依赖**：`pip install lark-oapi`（同步进 `requirements.txt`）。
6. **写适配层**：新增 `feishu_bot.py`（见 §5 模块 1/2/4/5/6/7）。
7. **配密钥**：`.env` 填 `FEISHU_APP_ID` / `FEISHU_APP_SECRET` / `FEISHU_ALLOWED_OPEN_IDS`。
8. **启动**：先起 API（`start_demo.cmd` 或只起 uvicorn），再 `python feishu_bot.py`。适配层可直接 `from erp_agent.agent import PurchasePOAgent` 在同进程调用（最省事），也可走 `http://127.0.0.1:8000`。
9. **自测**：飞书搜到机器人 → 单聊：
   - `查一下 MAT-FAB-001 的价格和包装费` → 验证只读查询；
   - 上传 `异常示例_BOM.xlsx` → `检测一下物料错误` → 验证文件落地与检测；
   - `根据 正常示例_BOM.xlsx 生成采购 PO 草稿` → 看金额 → 输入 `确认提交` → 验证写前确认与幂等。
10. **常驻**：把 `feishu_bot.py` 做成后台常驻（本机计划任务 / NSSM 服务 / Docker），保证电脑开机时在线。

## 7. 部署与安全注意事项

**部署**

- **常驻进程**：长连接要求进程一直在线；机器休眠/关机就掉线。长期用建议挂到常开的机器或小服务器上。
- **单实例**：内存 `sessions` + 长连接，**只跑一个进程**；不要起多个 worker 或多个容器副本，否则会话上下文会错乱。
- **API 与 bot 的关系**：同进程直调最简单；若分离，`api` 只需监听 `127.0.0.1`，不要暴露到公网。

**安全**

- **密钥**：`App Secret` 只进 `.env`，已被 `.gitignore`/`.dockerignore` 排除；不要写进代码或提交。
- **白名单**：`.env` 限定允许的 `open_id`，默认只服务自己，避免上线即对全公司开放。
- **写操作口令**：**保留「确认提交」文本口令**，不要在卡片上做"一键确认写入"——这是项目现有的核心安全设计，接飞书不该把它削掉。卡片按钮最多做到"回填 action_id + 仍需口令"。
- **入站校验**：长连接模式由 SDK 维护鉴权；若改用 Webhook 模式，必须按飞书要求做 `encrypt_key` / `verification_token` 校验。
- **数据边界**：项目只加载 `samples/`+`uploads/` 的合成数据，不接真实 ERP；飞书里也不要传真实业务 BOM。
- **日志**：飞书事件含 `open_id`/文本内容，日志里避免落敏感正文；`tool_trace` 建议只留工具名与步数。

| 能力 | 实现 |
|---|---|

| 群里行为 | 默认仅被 @ 时响应（`FEISHU_REQUIRE_MENTION_IN_GROUP`） |
| 并发 | 每消息起线程 + `Lock` 保护共享 sessions |

**已知限制**

- 内存 sessions：重启机器人会丢上下文；多实例不可用。
- 单进程：不要同时起多个 `feishu_bot.py`。
- 机器休眠/关机即掉线。
- 群里被 @ 时，正文里的 `@_user_x` 占位符已剥离，但复杂富文本（post/卡片）消息未解析。
