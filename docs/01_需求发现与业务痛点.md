# 01 需求发现与业务痛点

## 场景

外贸采购人员收到 BOM 后，需要核对物料档案、供应商、价格、包装费与币种，再生成采购 PO。该过程横跨表格、业务规则和 ERP 操作，适合用 Agent 降低查找与重复录入成本，但写入错误会直接产生业务风险。

本项目使用合成数据复现这一类通用流程。痛点来自流程抽象与 Demo 验证，不代表已在某家企业生产环境上线。

## 关键用户与任务

| 用户 | 目标 | 主要风险 |
|---|---|---|
| 录单员 / operator | 解析 BOM、发现物料错误、生成 PO 草稿并提交 | 编码错误、价格误算、重复建单、越权写入 |
| 审批人 / approver | 审核发起人提交的变更预览 | 自审、错误 action、未留审计 |
| 只读人员 / viewer | 查询档案、订单、审批与指标 | 越权修改 |
| FDE / 集成人员 | 将 Demo 能力适配客户测试 API | 鉴权泄露、超时、重复请求、厂商错误不稳定 |

## 待解决问题

1. BOM 字段和数据质量不稳定，错误常在录单后才暴露。
2. 人工跨表查档案并计算金额，耗时且容易遗漏包装费或币种约束。
3. 纯 LLM 生成业务数据不可审计，幻觉可能触发错误写入。
4. 单一操作者从发起到确认缺乏职责分离。
5. 客户 ERP 接口、认证和错误格式各异，业务逻辑不应绑定某个实现。
6. 出错时缺乏 request/session/action/tool 关联，难以定位故障层。

## 产品假设与验证方式

- 假设：模型适合做意图理解与工具编排，不适合决定金额和写入权限。用确定性工具、状态机与对抗评测验证。
- 假设：先预览、后审批、再明确确认能降低误写风险。用审计事件链和状态迁移测试验证。
- 假设：统一 Adapter 能降低客户联调改造面。用 SQLite 与 HTTP 两个实现及错误映射测试验证。
- 假设：面试现场应在 5 分钟内展示正常、阻断和审计三类证据。用固定演示脚本验证。
