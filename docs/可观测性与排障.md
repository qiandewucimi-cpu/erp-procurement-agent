# 可观测性与排障

## 目标与边界

本项目提供适合 Demo 和客户测试环境的轻量可观测性：结构化 JSON 日志、跨层关联标识与进程内指标。它用于快速证明“请求经过了哪些层、哪一层失败、耗时在哪里”，不冒充生产级 Prometheus、日志平台或分布式追踪系统。

日志默认输出到标准错误流，可由 Docker、进程管理器或本地启动器采集。设置 `.env` 中的 `LOG_LEVEL` 可调整级别。

## 关联链路

一次 API 调用会生成或接收 `X-Request-ID`，并在响应头原样返回。上下文按以下关系传播：

```text
request_id → session_id → actor_id → tool → action_id
                   └────→ LLM request
                              └────→ ERP HTTP request
```

- `request_id`：HTTP 请求级关联标识；调用方也可以主动传入。
- `session_id`：Agent 多轮会话标识。
- `actor_id`：鉴权层绑定的操作者身份。
- `action_id`：预览、审批、提交和回滚所围绕的业务动作。
- `tool`：模型实际调用的确定性业务工具。

日志不记录对话正文、BOM/订单载荷、Authorization 请求头、LLM API Key 或 ERP Token。字段名包含 `token`、`secret`、`authorization`、`api_key`、`password` 时会递归脱敏。

## 指标接口

访问 `GET /metrics` 可查看当前进程生命周期内的聚合指标：

```json
{
  "mode": "in_process_demo",
  "operations": {
    "http.request": {"total": 3, "success": 3, "failure": 0, "avg_ms": 4.2, "p95_ms": 5.1},
    "tool.create_purchase_order": {"total": 1, "success": 1, "failure": 0, "avg_ms": 12.4, "p95_ms": 12.4}
  }
}
```

可能出现的操作项包括 `http.request`、`agent.chat`、`llm.request`、`tool.<工具名>` 和 `erp_http.request`。指标只保存在内存中，重启后清零；RBAC 开启时 `/metrics` 需要至少 viewer 权限。

## 排障顺序

1. 调用 `/health`，确认 API、模型开关和鉴权模式。
2. 保存响应头中的 `X-Request-ID`，用它筛选同一次请求的 JSON 日志。
3. 查看 `/metrics`，判断失败集中在 HTTP、LLM、工具还是 ERP Adapter。
4. 若 `llm.request` 失败但确定性接口可用，检查模型地址、网络和 API Key；密钥不要粘贴进工单或截图。
5. 若 `erp_http.request` 重试后仍失败，检查客户测试 API、Bearer Token、超时配置和幂等键处理。
6. 若工具返回业务失败，使用 `action_id` 对照审批队列与审计日志，确认状态和操作者权限。

## 已知限制与生产演进

- 进程内指标不跨实例聚合，也不持久化。
- ContextVar 提供单进程异步上下文关联，不是完整 OpenTelemetry trace。
- 日志脱敏是兜底机制；调用点仍应遵守“只记录元数据、不传敏感载荷”的原则。
- 生产环境应接入集中式日志、Prometheus/OpenTelemetry、告警阈值、采样策略和数据保留制度。
