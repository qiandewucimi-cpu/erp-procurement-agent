# 09 项目复盘与面试问答

> 面试原则：先给结论，再说取舍与证据，最后主动说明边界。所有数字以仓库当前报告为准，不声称连接真实生产 ERP。

## 90 秒项目介绍

我把实习中接触过的 BOM 到采购 PO 流程抽象成一个可公开运行的安全 Agent，全部使用合成数据。模型通过 Function Calling 自主编排 8 个工具，但金额计算、字段校验、权限、审批状态迁移和写入都由确定性代码控制。高风险操作必须经过可信 action_id、operator/approver 职责分离和精确确认口令，重复提交保持幂等，并能审计和回滚。

工程上我用 ERPAdapter 隔离 SQLite Demo 与客户 HTTP API，覆盖鉴权、超时、重试和稳定错误映射；同时提供 FastAPI、Streamlit、MCP、飞书长连接和 Docker 入口。当前证据包括 98/98 单测、核心包覆盖率 89%、40/40 Agent 安全/能力评测，以及 14 条 RAG 评测中 Recall@3 100%、MRR 0.883、知识范围外拒答 100%。这些结果只证明仓库内合成场景，不代表已经生产上线。

## STAR 复盘

- Situation：人工在 BOM、物料档案、价格和 ERP 页面间搬运数据，容易漏填、错填或重复提交；直接让 LLM 写 ERP 风险过高。
- Task：构建一个可离线演示、可替换客户接口、能解释和阻断高风险动作的端到端作品。
- Action：拆出模型编排层与确定性业务层；建立 Adapter、RBAC/审批、幂等、审计、回滚、结构化日志；用对抗评测与 RAG 门禁持续验证。
- Result：正常合成 BOM 稳定生成 ¥24164 草稿，异常 BOM 被阻断；98/98 单测、40/40 Agent 评测、RAG 四项指标过门禁；已发布基线通过双 Python CI。

## 高频追问

### 1. 为什么这是 Agent，而不是固定工作流？

模型每轮根据上下文自主选择工具、参数、顺序和调用次数，`AgentLoop` 会把工具结果回填给模型继续规划。确定性回退流程只用于模型不可用时保障演示，不是 Agent 定义本身。证据：`erp_agent/llm.py`、工具轨迹和模型层评测。

### 2. 为什么不让模型直接算金额和写单？

采购金额与落库属于高风险、可精确表达的规则，交给概率模型会降低可审计性。模型只负责理解和编排，金额、校验和状态迁移由代码负责。这是“概率理解 + 确定性执行”的边界。

### 3. 如何防提示注入和越权？

系统不信任用户或模型声称的身份，也不信任它们提供的 action_id。身份由入口绑定；写工具校验角色、状态和职责分离；policy guard 只接受历史工具真实返回的 action_id，并要求当前消息完整等于“确认提交”。

### 4. 如何避免重复建单？

action_id 在本地状态中唯一，确认操作幂等；HTTP Adapter 继续向客户接口传递稳定 `Idempotency-Key`。并发测试验证多个确认只有一次成功写入。真实系统仍需数据库事务或服务端幂等配合。

### 5. 模型挂了怎么办？

模型请求失败会返回明确降级信息；固定业务 API 和离线烟测不依赖模型。写入仍受工具层约束，不会因模型超时绕过安全规则。生产方案还应加入熔断、队列和告警。

### 6. RAG 怎么评测？

用 10 条正向问题和 4 条知识范围外问题计算 Recall@1、Recall@3、MRR 和拒答命中率。首次基线的拒答只有 50%，加入最低相关性阈值和显式领域别名后达到 Recall@3 100%、MRR 0.883、拒答 100%。数据量很小，所以只作为回归门禁。

### 7. 为什么没直接上向量数据库？

当前知识只有少量 Markdown，词面检索更容易离线复现和解释。先建立指标再决定升级；真实客户语料出现同义表达、长文和规模问题后，再用 embedding + reranker，并用同一评测框架比较收益。

### 8. 如何接真实 ERP？

不改 Agent 业务接口，只替换 `ERPAdapter`。先在沙箱确认字段契约、权限、幂等、事务与错误码，再按只读、影子、受控写入推进。当前 HTTP Adapter 是契约样板，不等于完成真实联调。

### 9. 可观测性做到什么程度？

request/session/actor/action/tool 跨层关联，JSON 日志递归脱敏，`/metrics` 提供成功率和延迟。它适合 Demo 和测试环境；生产仍需 OpenTelemetry、集中日志、持久指标与告警。

### 10. 你遇到的最有价值问题？

一是并发确认可能重复写入，最终用唯一约束和事务式状态处理解决；二是 RAG 对无关问题返回低分伪引用，通过先测基线再设阈值解决；三是凭证失效导致模型评测 401，因此将环境故障和能力失败分开记录，避免用错误报告覆盖最近有效基线。

### 11. 如果再做一版会优先改什么？

拿到授权后先做真实测试租户契约测试与 SSO/IAM，而不是继续堆 UI；RAG 侧收集真实但脱敏的问题分布，再评估 embedding/reranker；运行侧加入集中追踪、告警和外部状态存储。

### 12. 你的个人贡献如何证明？

以 Git 提交、PR、CI、评测报告和 ADR 为证据，能够逐项定位设计决策、缺陷复现、修复和回归。业务背景来自流程抽象，代码与合成数据是个人作品实现。

## 不应使用的表述

- 不说“已接入公司生产 ERP”，应说“提供可替换 HTTP Adapter，并完成离线故障契约测试”。
- 不说“企业级 RAG”，应说“轻量可解释检索，建立 14 条合成评测门禁”。
- 不说“绝对安全”或“零幻觉”，应说“对已覆盖风险建立确定性约束和回归证据”。
- 不把当前 89% 核心包覆盖率或 100% 合成评测外推为真实客户效果。
