# 03 架构决策记录（ADR）

## ADR-001：受控工具调用，而非模型直写 ERP

- 状态：接受。
- 决策：模型只负责意图与工具编排；金额、校验、授权和状态迁移由确定性代码执行。
- 原因：保留 Agent 灵活性，同时让高风险决策可测试、可审计。
- 代价：工具 schema 和策略代码需要持续维护，能力边界比“任意自主执行”更窄。

## ADR-002：写入采用预览、审批、确认三道门

- 状态：接受。
- 决策：动作经过 DRAFT → PENDING_APPROVAL → APPROVED → COMMITTED，可回滚为 ROLLED_BACK；发起人不得自审。
- 原因：确认口令只能证明意图，不能替代身份和职责分离。
- 代价：演示步骤增加；默认关闭 RBAC 以保留单机体验，安全演示需显式开启。

## ADR-003：业务层依赖 ERPAdapter

- 状态：接受。
- 决策：SQLite 用于离线 Demo，HTTP 实现负责客户测试 API 的协议翻译、鉴权、超时、重试、错误映射和幂等头。
- 原因：客户系统差异应收敛在边界层，不污染 Agent 和业务工具。
- 代价：真实联调前仍需依据客户 OpenAPI 补字段映射、分页、限流与契约测试。

## ADR-004：多入口复用同一工具与权限层

- 状态：接受。
- 决策：Web、REST、MCP、飞书只做入口适配，身份在入口绑定，业务工具不信任模型传入的 operator。
- 原因：避免不同入口形成安全旁路。
- 代价：每个入口都必须正确完成身份映射。

## ADR-005：轻量可观测性先满足 Demo 排障

- 状态：接受。
- 决策：使用 JSON 日志、ContextVar 和内存指标，保留未来接 OpenTelemetry/Prometheus 的升级路径。
- 原因：在单机作品中以较低复杂度证明诊断思路。
- 代价：指标不持久、不跨实例，不能替代生产监控平台。

## ADR-006：CI 默认确定性评测，模型评测手动全量运行

- 状态：接受。
- 决策：CI 跑 25 条离线场景；配置模型后手动跑含 15 条模型场景的 40 条全量评测。
- 原因：控制外部网络、费用和模型漂移导致的不稳定。
- 代价：全量报告需注明模型与运行时间，不能假定永久复现同一结果。
